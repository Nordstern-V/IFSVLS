# PYNQ 工程移植与排障

将问题定位到能够解释现象的最早失败层，完成当前任务所需的最小修复，并明确哪些结论来自源码、主机测试和实板结果。优先保留已经工作的硬件链路、模型和数据。

## 从现有状态继续

先检查用户指定的主工程、当前源码版本、近期改动、部署文件和最新日志；已有可用工程或阶段成果时从该处继续，不重新初始化整个项目。源码优先于过期的状态文档，用户最新现场描述优先于之前对故障时间的推测。

建立本次任务需要的环境事实，而不是要求用户填写整套配置表：

- 板卡及器件、镜像/PYNQ/Python、Vivado 与实际使用的解释器；区分 Windows 主机、网络共享目录和板端运行目录。
- 当前加载的 `.bit/.hwh`、IP 名称/VLNV/地址、时钟复位及模型/缓存版本；同名文件不证明来自同一次构建。
- 最小触发动作、最早异常、是否仍有视频/事件/心跳；`touch_error=None` 只表示尚无异常文本，不证明驱动正在前进。

有本地访问能力时直接读取；只有缺失的板端事实才请用户补充一组短命令或一次有针对性的实验。可按需把 [状态采集脚本](scripts/collect_pynq_state.py) 复制到板端运行：它只读文件和状态，不下载 Overlay、不访问 IIC、不复位或写启动分区。Windows 上运行得到的是主机信息，不能当作板端状态。

## 用证据决定修复

1. **先分层**：板级电气/引脚 → PL IP/时钟复位/AXI → Linux 设备树/驱动 → PYNQ 包装/API → 数据契约 → 应用状态与交互。按现象缩小范围，不机械重跑所有层。
2. **设一个可观测判据**：例如 Host root hub 出现、触摸事务计数继续增长、视频帧序号变化、输出包含指定维度的有限值；明确该观测能排除什么。
3. **先单模块，再并行整机**：独立验证通过而组合失败时，保留两种上下文，比较初始化顺序、线程/进程、资源持有、库调用及异常后的恢复，不把单模块 PASS 当成整机 PASS。
4. **改可解释的原因**：核实寄存器协议和驱动实现后修复；软件 API 问题不先重建 PL，内核没有注册 Host 不先更换键盘库，慢循环或 C 层阻塞不只增加轮询间隔。
5. **复验原触发动作与持续工作**：看门狗打印“成功”后仍需验证新触摸事件及后续多次交互；只验证控制器能被检测到还不够。

尽量复用已有工具和脚本。未知 IP 参数/寄存器查对应版本的本地驱动、IP 文档或厂商主源，不猜 `CONFIG.*`。无错误返回不等于配置生效；读回参数、地址和接口。没有专用 MCP 时可使用现有 CLI/Python，不依赖本 skill 之外的示例插件。

## 保留实现边界

- 一个应用生命周期优先复用一个有效 Overlay；下载会改变 PL 状态，确需重载时先停止并释放旧使用者。
- 同一不支持并发的加速器串行提交；视频与 UI 不在前台同步等待长推理。恢复流程必须先处理旧执行者，避免新旧进程同时写同一外设。
- 非阻塞超时应覆盖真正可能阻塞的调用；Python 线程外加计时器不能保证打断底层 C 调用。
- 将类别 ID、显示名称、样本特征、预处理版本和模型维度分别校验；旧学习文件不应仅因新增名称而失效。
- 请求回退某个算法时只恢复该范围，保留用户明确要求保留的键盘、数字、计算器及数据；用可用的旧版作为行为参照，不整体覆盖新工程。
- 不把本例 FT 地址、GPIO 引脚、100 ms 轮询、80D 特征或 USB0 设备树补丁写成通用规则。

## 验证与交付

对改动选择最有区分力的检查：API/状态转换用 fake 对象，模型边界用确定性输入，IIC/USB/视频用实际设备。适当复用现有测试；简单文档或可逆低影响修改不另造测试框架。

结论分别写清：**已修改、主机已验证、实板已验证、仍需验证**。重复输出稳定不代表准确率达标，NCM/余弦百分比不等于校准正确率，正 WNS 也不能掩盖无时钟或未约束端点。

交付最小文件清单、板端准确路径和解释器命令、启动应显示的版本、原故障复验步骤，以及必要的备份/回退办法。保留已有学习 NPZ 和支持库；仅在模型或预处理契约改变时说明是否需重建。

常规已授权修复直接完成；烧写、启动分区修改、重启及硬件接线按用户当前授权范围执行，不从参考案例推导权限。涉及启动文件时先识别实际启动镜像、验证目标与备份，再做受控替换；不匹配时保留诊断并停止该写入。
