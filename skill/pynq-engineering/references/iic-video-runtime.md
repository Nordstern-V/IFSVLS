# IIC、视频与运行恢复

## GPIO API 与触摸寄存器事务

先区分 PYNQ 的 GPIO controller、channel 和 pin/slice 对象；它们的 `write` 签名可能不同。本例旧驱动曾要求 `write(value, mask)`，不能把对任何对象的 `write(value)` 都视为正确，也不要用大范围捕获 TypeError 掩盖别的编程错误。确认方向、通道位宽、复位极性和可用对象的真实实现。

FT/GT 等控制器的寄存器宽度、地址与读取/清状态协议各有差异。对要求 repeated START 的读取，事务应为：

```text
START + 从地址(W) + 寄存器地址
REPEATED START + 从地址(R) + 数据 + STOP
```

保持总线的地址阶段之后调用“等总线空闲”，可能在合法的 busy 状态下超时。要结合实际 AxiIIC 的 send/receive/wait 参数与源码确定 STOP 时机，并校验 cffi buffer、收发返回值及 7 位地址约定。不要把所有 IIC 器件都改成同一事务。

只修改协议允许的状态寄存器。对连续触摸，状态与坐标分开读取可能得到不同时间的快照；清状态时机也可能破坏连续事件。先查控制器和参考实现，再选择一致读取/清除方式。

## 独立验证通过，整机一触摸就错

比较两边的驱动版本、解释器、初始化顺序、Overlay 是否被后续重载、同一控制器是否有多个使用者，以及触摸发生时具体进入的事务分支。用户纠正“第一触摸就触发”时，不再沿用“运行几十秒才出错”的推断。

观察触摸进程/线程每次请求的开始、结束、事务计数、最近成功时间和心跳；对不同失败分支保留原始异常。纯粹每隔几秒打印同一个 `touch_error=None` 无法检出卡在底层的调用。

增加轮询间隔只能改变负载，不修复 repeated START、竞争或 C 函数永久等待。INT 门控与释放保护应基于该控制器电平含义、事件行为和实测；不要从本例复制极性或固定周期。

## 可终止的恢复

先尝试有边界的事务超时和已验证的 IP/控制器复位。如果底层 C 调用阻塞、线程取消不能打断，可考虑独立进程隔离访问，并由父进程监测心跳。Linux fork 模式应尽量在其他线程启动前建立；后续重建还需处理继承的 fd、锁和库状态，不是跨操作系统的通用办法。

恢复一次时停止旧使用者，确认其已经退出，再执行已核对的触摸/控制器复位和重新初始化，重建唯一的访问者。不能保留旧线程同时启动新线程争用总线。

恢复必须可结束：限定一次恢复的各阶段等待与连续失败次数；使用退避防止重置风暴。经过少量有依据的尝试仍无新成功事务时，保留明确的 unavailable 状态和诊断，允许不依赖触摸的界面继续运行；等待新证据或外部状态改变，不永久循环复位。

`SOFTR=0x40, value=0xA` 仅是本例所用 AXI IIC 的已核对协议，换 IP 前要重新核对；它不是“任何 I2C 都这样复位”的规则。

验收恢复：短点、长拖动、松手、连续按键、模式来回切换，覆盖原先容易失败的动作；看恢复后的事件序号/时间是否继续前进。不能只凭“watchdog recovery=ok”或再次读到芯片 ID 宣告恢复完成。

## 视频首帧正常后定格 / 退出困难

分别检查：摄像头是否产生新帧、VDMA 输入是否前进、CPU 是否取到新缓冲、显示端是否消费、应用是否在前台等待 IIC/推理。画面不变可能是主动 FREEZE、原始帧缓存或显示旧帧，不一定是摄像头采集停了。

核对当前镜像的 camera/video 驱动实现、显示模式、输入输出关联与预热要求。本例使用 `video_in.tie(video_out)`，不能将这个调用不加检查地套用到所有 PYNQ 视频管线。

明确 DMA 帧所有权：取得帧 → 读取原始 ROI / 生成必要副本 → 叠加 UI → 输出或归还；已交给输出通路的帧不再自行释放，中断时未提交的帧只释放一次。异步任务用独立 ROI 副本，不持有将被归还的 DMA 帧引用。

推理放到后台，按设备能力串行化。冻结画面可以保存普通内存中的原始帧副本，同时继续消费视频输入；不要把停止取帧自动等同于正确的冻结实现。

对驱动无限等待，使用该接口支持的有限等待或停止条件，确保检查点覆盖真实阻塞处；定时器变量本身不会让阻塞读返回。退出时停止工作、释放设备/缓冲，并检查反复启动是否还能初始化。

## UI 状态与过期结果

ROI、模式或识别类型改变时，用请求代次/标识使旧异步结果失效，防止将上个框的特征、名称或数字提交到新框。触摸和键盘按同一单调时间基准合并；输入断开/丢失时取消不完整编辑并重置修饰键。

高频 move 日志可以限流，但不应因此减少必要事件；将“日志打印慢”与“事件真的未到达”分开测量。持续运行时的帧率、输入延迟、TCU 耗时和恢复次数分别观察。
